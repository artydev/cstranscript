AudioTranscript

A Blazor Server application that transcribes audio files of arbitrary size by splitting them into raw chunks, re-encoding each chunk server-side with FFmpeg, and submitting them to a Whisper-compatible speech-to-text API over Server-Sent Events.

Stack ASP.NET Core · Blazor · HTMX
API Albert / OpenAI Whisper-compatible
Re-encoder FFmpeg (server-side)
Real-time SSE (Server-Sent Events)
01

Purpose & Architecture

TranscriptAudio solves a concrete problem: Whisper-compatible APIs impose a hard upload limit (typically 25 MB), but real-world audio recordings — meetings, interviews, lectures — routinely exceed this threshold. The application handles files of any size transparently, hiding all chunking complexity from the user.

Rather than re-encoding audio on the client (which required loading the entire decoded PCM buffer into browser RAM), the current architecture delegates all audio processing to FFmpeg running on the server. The client sends raw binary slices; the server converts each slice to a valid mono 16 kHz WAV before passing it to Whisper.

Small files (< 12 MB)

Handled directly by HTMX — a single POST to the transcription endpoint, no JavaScript pipeline involved. Response is rendered as an HTML fragment.

Large files (≥ 12 MB)

HTMX submission is intercepted. The JS pipeline takes over: slices the file into 10 MB raw chunks and sends them sequentially, streaming progress via SSE.

Operating Modes

The application has two distinct code paths depending on file size, sharing the same Whisper backend.

Mode A — Direct HTMX (small files)

When the uploaded file is below CHUNK_LIMIT (12 MB), the default HTMX form submission proceeds unmodified. The entire file is POSTed in a single request. The server transcribes it and returns an HTML fragment that HTMX swaps into the output element. No custom JavaScript runs.

Mode B — JS Chunk Pipeline (large files)

When the file meets or exceeds CHUNK_LIMIT, the htmx:confirm event is intercepted and lancerPipelineChunk() is called instead. The pipeline is strictly sequential:

1
Slice — file.slice(offset, offset + CHUNK_SIZE) produces a zero-copy Blob view. No bytes are copied into JS heap.
2
POST — each chunk is sent as multipart/form-data with its index, total count, original file extension, and a shared sessionId.
3
FFmpeg — server writes raw bytes to a temp file, spawns FFmpeg, reads the output WAV path. No audio data in managed memory.
4
Whisper — the WAV is streamed to the Whisper API from disk via FileStream. Response is parsed for the text field.
5
SSE (per-chunk) — client awaits the per-chunk SSE stream to completion before sending the next chunk. Natural back-pressure, no rate-limit timer needed.
6
Session SSE — once all chunks complete, the session channel emits the final reassembled text. The per-chunk texts are joined in order.

pipelinechunk.js CLIENT

.js wwwroot/js/pipelinechunk.js

Self-contained IIFE that intercepts HTMX form submissions for large files and orchestrates the entire client-side chunking pipeline. Has no external dependencies — vanilla JS only.

  • Displays the selected filename and size in the UI on file input change.
  • Intercepts htmx:confirm and routes large files to the chunk pipeline.
  • Slices the file into raw Blob chunks without loading file content into memory.
  • POSTs each chunk sequentially with sessionId, index, total, and the original file extension.
  • Opens and reads the per-chunk SSE stream, updating the output element in real time.
  • Opens the session SSE channel once (on first chunk) and awaits the final assembled text.
  • Updates the progress bar and status label throughout the pipeline.

Key Functions

slicerFichier(file, chunkSize)

Synchronous generator. Computes total = Math.ceil(file.size / chunkSize) before the first yield — no accumulation needed. Each iteration yields { blob, index, total }. Blob.slice() is a zero-copy pointer into the browser's file handle; no bytes enter the JS heap.

lireSSE(response)

Async generator over a ReadableStream. Splits on \n\n, filters for data: prefixed lines, and yields the payload string. The finally block guarantees reader.releaseLock() even if the consumer breaks early or throws. Handles the trailing-buffer edge case (stream ending without a final \n\n).

lancerPipelineChunk(file)

Main async pipeline driver. Uses a plain for...of loop (not for await...of) since slicerFichier is synchronous. Each iteration awaits the full SSE stream for that chunk before proceeding — this provides natural back-pressure and makes a rate-limit delay unnecessary.

extOf(name)

Extracts the file extension from the original filename and appends it to the chunk filename (chunk_0.mp3, chunk_1.mp3…). FFmpeg uses this extension to detect the input container format. Falls back to .bin for extensionless files.

ℹ
Why no rate-limit delay? The pipeline awaits each chunk's SSE stream to completion before sending the next chunk. Only one chunk is ever in-flight at a time, so a fixed sleep() between sends would only add dead time on top of an already sequential flow. 
// Zero-copy slicer — synchronous generator
function* slicerFichier(file, chunkSize) {
    const total = Math.ceil(file.size / chunkSize);  // known upfront
    let offset  = 0;
    let index   = 0;
    while (offset < file.size) {
        yield { blob: file.slice(offset, offset + chunkSize), index, total };
        offset += chunkSize;
        index++;
    }
}

Program.cs SERVER

.cs Program.cs (project root)

Application entry point and composition root. Configures Kestrel limits, registers all services into the DI container, builds the HTTP middleware pipeline, and maps every endpoint. Contains all routing logic — no controllers, no Razor Page code-behind.

  • Sets Kestrel and ASP.NET Core form limits to 101 MB (100 MB file + 1 MB overhead).
  • Binds WhisperConfig and ProxyConfig strongly-typed option classes from appsettings.json.
  • Registers TranscriptionStatusTracker and WhisperService as singletons.
  • Configures the named "Whisper" HttpClient with base URL, bearer token, 15-minute timeout, and optional proxy.
  • Applies a /transcript path base in non-development environments (IIS sub-application support).
  • Maps three endpoints: SSE stream GET, single-file POST, chunk POST.

Size Limits Configuration

Two independent limits must both be raised. Kestrel enforces the raw TCP body size; ASP.NET Core's form parser enforces the multipart section size. Both must accommodate the maximum expected upload — set here to 100 MB with 1 MB overhead for multipart boundaries. 

const long MaxFileSize = 100 * 1024 * 1024; // 100 MB

// Kestrel — raw TCP body
builder.WebHost.ConfigureKestrel(options =>
    options.Limits.MaxRequestBodySize = MaxFileSize + (1024 * 1024));

// ASP.NET Core — multipart form section
builder.Services.Configure<FormOptions>(options =>
    options.MultipartBodyLengthLimit = MaxFileSize + (1024 * 1024));
⚠
IIS overrides these limits. Even with Kestrel configured correctly, IIS applies its own maxAllowedContentLength before the request reaches Kestrel. The web.config entry (section 09) must also be set, or IIS will return HTTP 413 before ASP.NET Core sees the request.

HttpClient — Named "Whisper"

The Whisper HTTP client is configured via the typed options pattern. The base URL and API key are read from WhisperConfig (bound from the Whisper section) and will throw InvalidOperationException at startup if either value is missing — failing fast rather than at the first transcription request. 

builder.Services.AddHttpClient("Whisper", (sp, client) => {
    var config = sp.GetRequiredService<IOptions<WhisperConfig>>().Value;
    client.BaseAddress = new Uri(config.ApiTranscript
        ?? throw new InvalidOperationException("API URL manquante"));
    client.Timeout = TimeSpan.FromMinutes(15);
    client.DefaultRequestHeaders.Authorization =
        new AuthenticationHeaderValue("Bearer", config.ApiKey
            ?? throw new InvalidOperationException("API Key manquante"));
}).ConfigurePrimaryHttpMessageHandler(sp => {
    var proxy = sp.GetRequiredService<IOptions<ProxyConfig>>().Value;
    return proxy.UseProxy && !string.IsNullOrWhiteSpace(proxy.Url)
        ? new HttpClientHandler { Proxy = new WebProxy(proxy.Url), UseProxy = true }
        : new HttpClientHandler();
});

Endpoints

GET /transcribe-sse/{id:guid}

Dual-purpose SSE stream endpoint. The same route serves both per-chunk channels (short-lived, one per chunk) and the session channel (long-lived, one per file upload). The distinction is purely by the GUID passed — chunkId or sessionId.

  • Sets Content-Type: text/event-stream and X-Accel-Buffering: no (disables nginx/IIS output buffering).
  • Subscribes to the TranscriptionStatusTracker channel for the given id.
  • Strips newlines from HTML payloads before writing — SSE data: lines must not contain raw CR/LF.
  • Flushes after every write to ensure the browser receives each event immediately.
  • Calls tracker.Unsubscribe(id) in finally to clean up the channel on client disconnect or completion.

POST /transcribe-audio

Handles single-file uploads (small files routed through HTMX directly). Saves the file to a temp path, enqueues it in WhisperService, then returns an HTML fragment rendered by TranscriptionSseBridge — a Blazor component that initialises the SSE listener on the client side.

ℹ
TranscriptionSseBridge is a Blazor component rendered server-side to HTML, similar to TranscriptionResult. It renders a self-contained SSE listener (JavaScript included) that connects to /transcribe-sse/{id} and updates the output element. It is the bridge between the HTMX response and the SSE stream.

POST /transcribe-chunk

Receives one raw chunk at a time from the JS pipeline. Validates all required form fields (AudioFile, index, total, sessionId), reads the chunk bytes into a MemoryStream, then hands them to WhisperService.EnqueueChunkAsync().

⚠
Case-sensitive field name. The form field is read with form.Files.GetFile("Audiofile") — note the lowercase f in file. The JS client sends it as AudioFile (capital F). This mismatch will cause every chunk POST to return HTTP 400. Verify both sides use the identical casing.

On success, returns a JSON object with both SSE URLs. The JS client uses sseUrl immediately for per-chunk progress and opens sessionSseUrl once on the first chunk, keeping it open until the final assembled text arrives. 

// Response shape from POST /transcribe-chunk
{
  "sseUrl":        "/transcribe-sse/{chunkId}",    // short-lived
  "sessionSseUrl": "/transcribe-sse/{sessionId}", // long-lived
  "chunkId":       "guid",
  "index":         0,
  "total":         4,
  "sessionId":     "guid"
}

Path Base

In non-development environments, app.UsePathBase("/transcript") is applied. This enables the application to run as an IIS sub-application under https://yourserver/transcript/ without breaking static file paths or redirects. All SSE URLs computed in endpoints are prefixed accordingly via the sseBase variable.

WhisperService.cs SERVER

.cs Services/WhisperService.cs

Singleton background service that manages a bounded channel queue of transcription requests, spawns a configurable worker pool, orchestrates FFmpeg re-encoding, calls the Whisper API, and publishes results back to clients via SSE. Implements IAsyncDisposable for clean shutdown.

  • Maintains a Channel<TranscriptionRequest> as a bounded work queue (capacity = MaxConcurrent × 2).
  • Spawns MaxConcurrent background workers, stores their Task[] for clean disposal.
  • Writes raw chunk bytes to a temp file at enqueue time — byte[] never enters the channel buffer.
  • Spawns FFmpeg as a child process, converting any input format to mono 16 kHz WAV on disk.
  • Streams the WAV file directly to Whisper via FileStream — no byte[] in managed heap.
  • Tracks multi-chunk sessions in a ConcurrentDictionary, assembles final text in order once all chunks complete.
  • Publishes progress and final HTML to subscribers via TranscriptionStatusTracker.
  • Properly unsubscribes SSE channels on all exit paths (success, error, session completion).

Concurrency Model

The service uses a producer/consumer pattern. The HTTP controller is the producer; worker tasks are consumers. The bounded channel applies back-pressure: if all workers are busy and the buffer is full, WriteAsync on the producer side will await automatically.

ComponentTypeRole
_queueChannel<TranscriptionRequest>Bounded work queue. Capacity = MaxConcurrent × 2.
_workersTask[]Background consumers. Stored for graceful shutdown.
_sessionsConcurrentDictionary<Guid, TranscriptionSession>In-flight multi-chunk sessions. Keyed by sessionId.
_retryPolicyPolly IAsyncPolicyExponential backoff (3 retries) on HttpRequestException.
_ctsCancellationTokenSourceSignals worker cancellation on disposal.

FFmpeg Integration

ReencodeWithFfmpegAsync() converts a raw chunk (any format) to a frame-aligned mono 16 kHz WAV. This step is critical: MP3 and WebM files sliced at arbitrary byte offsets produce invalid frame boundaries that cause Whisper to return HTTP 500 errors. FFmpeg repairs the stream and outputs a clean WAV regardless of input container. 

ffmpeg -y -i "inputPath" -ar 16000 -ac 1 -f wav "outputPath"
⚠
stderr before WaitForExitAsync. StandardError is read to completion before calling WaitForExitAsync(). This is intentional: if the process fills its stderr pipe buffer and no one is reading it, the process blocks — causing a deadlock with WaitForExitAsync. Reversing the order would hang on any verbose FFmpeg output.

Memory Strategy

The key design goal is to never hold full audio data as a managed byte[] in the .NET heap. The flow is entirely disk-based after the initial controller write:

StageStorageLifetime
EnqueueChunkAsyncWrite to temp file, discard byte[]Until ReencodeWithFfmpegAsync reads it
ReencodeWithFfmpegAsyncInput temp file → FFmpeg → output WAV temp fileUntil Whisper POST completes
CallWhisperApiFromFileAsyncFileStream (no byte[] allocation)Duration of HTTP POST
Cleanup (finally)Both temp files deletedImmediate after POST

Session Assembly

Each chunk request carries an Index and is stored in TranscriptionSession.Texts[] at the correct position. A lock on session.Lock protects the counter increment and array write (no await inside the lock, so no async deadlock risk). Once CompletedCount == Total, the texts are joined with spaces and published on the session SSE channel.

Disposal

DisposeAsync() completes the channel writer (signals workers to drain and exit), cancels the CancellationTokenSource, then awaits all worker tasks with a 10-second timeout. This ensures in-flight FFmpeg processes and Whisper calls are not orphaned on application shutdown. 

public async ValueTask DisposeAsync() {
    _queue.Writer.TryComplete();
    await _cts.CancelAsync();
    try {
        await Task.WhenAll(_workers)
            .WaitAsync(TimeSpan.FromSeconds(10));
    }
    catch (OperationCanceledException) { /* expected */ }
    catch (TimeoutException) {
        _logger.LogWarning("WhisperService: forced shutdown after 10s timeout.");
    }
    _cts.Dispose();
}

TranscriptionStatusTracker.cs SERVER

.cs Services/TranscriptionStatusTracker.cs

Singleton in-memory pub/sub broker that connects background transcription workers to SSE endpoint handlers. Each active SSE connection maps to one unbounded Channel<string>. Workers write HTML payloads; the SSE endpoint reads and forwards them to the browser.

  • Maintains a ConcurrentDictionary<Guid, Channel<string>> — one entry per active SSE subscription.
  • Subscribe(id) — creates a new unbounded channel, registers it, returns the reader to the SSE endpoint.
  • NotifyUpdate(id, html) — writes an HTML string to the channel identified by id. No-op if the id has no subscriber (client disconnected).
  • Unsubscribe(id) — removes the channel and calls TryComplete() on the writer, which causes the SSE endpoint's ReadAllAsync loop to exit cleanly.
  • HasSubscriber(id) — polled by WhisperService.WaitForSubscriberAsync() before sending the first update, ensuring the browser SSE connection is open before processing begins.

Channel Lifecycle

Every GUID that flows through the system — both chunkId and sessionId — gets its own independent channel. The lifecycle is always:

1
Subscribe — SSE endpoint calls Subscribe(id) when the browser opens the connection. Channel is created and the reader is held by the endpoint's await foreach loop.
2
NotifyUpdate (n times) — WhisperService writes progress HTML as processing advances. Each write unblocks the await foreach in the SSE endpoint, which immediately flushes it to the browser.
3
Unsubscribe — called by WhisperService after the final message, or by the SSE endpoint's finally block on client disconnect. TryComplete() closes the writer, which terminates the reader loop.

Two Channel Types in Practice

Channel keyed byLifetimeWritten byRead byClosed when
chunkId Short — one per chunk WhisperService.ProcessChunkRequestAsync SSE endpoint (per-chunk progress) TraiterChunkTranscritAsync after chunk final message
sessionId Long — one per file upload WhisperService.TraiterChunkTranscritAsync (last chunk only) SSE endpoint (session final text) TraiterChunkTranscritAsync after full text assembled

Why Unbounded Channels

Channel.CreateUnbounded<string>() is used rather than bounded. The SSE endpoint drains the channel as fast as the network allows, and workers write infrequently (a handful of status strings per chunk). There is no realistic risk of unbounded growth — each channel holds at most a few HTML strings before they are consumed. A bounded channel would add complexity (back-pressure, write failures) with no practical benefit here.

ℹ
Double Unsubscribe is safe. ConcurrentDictionary.TryRemove is a no-op if the key is absent, and Channel.Writer.TryComplete() is idempotent — calling it on an already-completed channel returns false without throwing. Both the SSE endpoint finally block and WhisperService call Unsubscribe independently; neither will fault if the other runs first. 
// Full implementation
public class TranscriptionStatusTracker
{
    private readonly ConcurrentDictionary<Guid, Channel<string>> _streams = new();

    public ChannelReader<string> Subscribe(Guid id)
    {
        var channel = Channel.CreateUnbounded<string>();
        _streams[id] = channel;
        return channel.Reader;
    }

    public async Task NotifyUpdate(Guid id, string html)
    {
        if (_streams.TryGetValue(id, out var channel))
            await channel.Writer.WriteAsync(html);
    }

    public void Unsubscribe(Guid id)
    {
        if (_streams.TryRemove(id, out var channel))
            channel.Writer.TryComplete();
    }

    public bool HasSubscriber(Guid id) => _streams.ContainsKey(id);
}

TranscriptionResult.razor UI

.razor Components/TranscriptionResult.razor

Stateless Blazor component used exclusively for server-side HTML rendering. It is never mounted in the browser — WhisperService uses HtmlRenderer to render it to an HTML string, which is then emitted as an SSE payload.

  • Accepts three parameters: Message (string), IsError (bool), IsProcessing (bool).
  • Renders a processing state with a spinner animation when IsProcessing is true.
  • Renders an error state with a warning icon when IsError is true.
  • Detects the keyword "Conversion" in the message to show a purple 🔧 icon during the FFmpeg re-encoding step.
  • Renders the final transcribed text as formatted output when both flags are false.
ℹ
Server-side rendering only. This component is rendered to a raw HTML string via renderer.RenderComponentAsync<TranscriptionResult>() inside WhisperService.SendUpdate(). The resulting HTML is sent as an SSE data: payload. The client sets output.innerHTML = html on receipt. No Blazor SignalR circuit is involved.

Security

⚠ Never commit API keys to source control

The OpenAI:ApiKey value must never appear in appsettings.json or any file tracked by git. If a key has been committed, rotate it immediately — git history retains it even after removal.

Use ASP.NET Core User Secrets in development and environment variables in production.

Development (User Secrets)

dotnet user-secrets set "OpenAI:ApiKey" "sk-your-key-here"

User secrets are stored in %APPDATA%\Microsoft\UserSecrets\<userSecretsId>\secrets.json on Windows — outside the project directory and therefore outside git.

Production (Environment Variables)

# Windows Server — double underscore = section separator
set OPENAI__APIKEY=sk-your-key-here

# or in IIS Application Pool → Environment Variables
OPENAI__APIKEY = sk-your-key-here

ASP.NET Core's configuration system merges environment variables over appsettings.json automatically. The double underscore (__) maps to the colon (:) section separator in JSON keys.

IIS / web.config

IIS applies a default request size limit of 30 MB (or lower depending on configuration). Since raw audio chunks can reach 10 MB and multipart overhead adds a small margin, the limit must be explicitly raised to at least 15 MB. 

<!-- web.config -- add or merge into system.webServer -->
<system.webServer>
  <security>
    <requestFiltering>
      <requestLimits maxAllowedContentLength="15728640" />
    </requestFiltering>
  </security>
</system.webServer>
ℹ
15728640 = 15 MB. Chunks are 10 MB raw. The 15 MB limit provides 5 MB of headroom for multipart form boundaries and metadata. The JS CHUNK_LIMIT threshold (12 MB) and CHUNK_SIZE (10 MB) are both below this ceiling.

FFmpeg Installation on Windows Server

# Option 1 — winget
winget install ffmpeg

# Option 2 — Chocolatey
choco install ffmpeg

# Option 3 — manual
# Place ffmpeg.exe anywhere and set the full path in appsettings.json:
"Whisper:FfmpegPath": "C:\\tools\\ffmpeg\\bin\\ffmpeg.exe"
