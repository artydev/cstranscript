This document analyses the source code that belongs to the TranscriptAudio.Presentation.JSChunk namespace. It covers the project structure, the main entry point, UI components, services, configuration, request flow and key architectural points.

2. Program.cs – Bootstrap & Routing

  • DI registration
    • TranscriptionStatusTracker – singleton, holds Channel<string> per transcription ID.
    • WhisperService – singleton, queues jobs, calls Whisper, publishes results.
    • WhisperConfig and ProxyConfig – bound from configuration.
  • Kestrel limits – request body size limited to 100 MiB (+1 MiB margin).
  • Endpoints
    • GET /transcribe-sse/{id:guid} – generic Server‑Sent Events endpoint. Reads from TranscriptionStatusTracker and streams HTML fragments.
    • POST /transcribe-audio – receives a whole audio file, stores it temporarily, enqueues a transcription job, builds an SSE URL and returns a rendered TranscriptionSseBridge fragment.
    • POST /transcribe-chunk – receives a single chunk (with index, total, sessionId), enqueues it, and returns JSON containing:
      • sseUrl – per‑chunk progress channel.
      • sessionSseUrl – long‑lived channel for the whole session.
      • identifiers (chunkId, sessionId, index, total).

3. UI Components (Components folder)

ComponentResponsibility
TranscribeAudio.razorRenders a file‑upload form, posts the selected file to /transcribe-audio, and injects the returned HTML (the SSE bridge) into the page.
TranscriptAudioRecorder.razorImplements a client‑side audio recorder using the MediaRecorder API, slices the recording into blobs, and posts each blob to /transcribe-chunk. The first chunk also opens the session SSE.
TranscriptionResult.razorDisplays the final transcription text. It receives HTML fragments from the SSE channel and updates its markup.
TranscriptionSseBridge.razorServer‑side component rendered after a POST. Contains a <script> that opens an EventSource to the supplied SseUrl, listens for message events and injects the received HTML into a target container.

4. Services

4.1 TranscriptionStatusTracker.cs

  • Maintains ConcurrentDictionary<Guid, Channel<string>>.
  • Subscribe(Guid id) – returns a ChannelReader<string> for SSE.
  • Publish(Guid id, string html) – writes a new HTML fragment to the channel.
  • Unsubscribe(Guid id) – completes and removes the channel.

4.2 WhisperService.cs

  • EnqueueTranscriptionAsync – called from /transcribe-audio. Stores the temporary file path, creates a job, calls the Whisper HTTP API, renders the result via HtmlRenderer and publishes it through the tracker.
  • EnqueueChunkAsync – called from /transcribe-chunk. Receives raw byte[] for a chunk, forwards it to Whisper, publishes per‑chunk progress (using chunkId) and accumulates partial results. When the last chunk arrives, concatenates all parts, renders the final HTML and publishes it on the sessionId channel.
  • Uses the named HttpClient "Whisper" (configured with base address, timeout, bearer token, optional proxy).
  • Relies on HtmlRenderer to turn Razor components (TranscriptionResult) into HTML strings for SSE.

5. Configuration (Config folder)

  • WhisperConfig.cs – ApiTranscript (base URL) and ApiKey. Populated from the Whisper section of appsettings.json.
  • ProxyConfig.cs – UseProxy and Url. If enabled, the Whisper HttpClient is built with a WebProxy.

6. End‑to‑End Flow (high‑level)

  1. User selects a file or records audio in the browser.
  2. Browser posts to /transcribe-audio (whole file) or /transcribe-chunk (individual chunk).
  3. Server stores the payload, creates a GUID, and enqueues a job in WhisperService.
  4. WhisperService calls the external Whisper API, receives transcription text.
  5. The service renders a Razor component (TranscriptionResult) to an HTML snippet using HtmlRenderer.
  6. The snippet is sent to TranscriptionStatusTracker, which pushes it into the appropriate Channel<string>.
  7. The client‑side EventSource (opened by TranscriptionSseBridge) receives the data: … payload, strips the wrapper and injects the HTML into the page, giving the user real‑time progress.
  8. When all chunks are processed, the accumulated text is rendered once more and streamed on the long‑lived session SSE channel.

7. Architectural Highlights

  • Separation of concerns – UI (Razor components), business logic (services), and progress transport (SSE) are cleanly isolated.
  • Server‑Sent Events – lightweight push mechanism; no WebSocket overhead.
  • Chunked upload support – enables processing of large files (> 25 MiB) that are sliced client‑side.
  • Dependency injection – all services, configuration and the named HttpClient are injected via the built‑in container.
  • Server‑side HTML rendering – re‑uses Razor components for incremental updates, ensuring consistent UI.

8. Points to Consider (future work)

  • Error handling – ensure WhisperService publishes user‑friendly error fragments when the Whisper API fails.
  • Chunk ordering – current logic assumes in‑order delivery; out‑of‑order chunks would need sequencing logic.
  • Temporary file cleanup – delete whisper_{id}.tmp after processing to avoid disk bloat.
  • Scalability – the in‑memory tracker and session dictionaries are process‑local; a distributed cache (e.g., Redis) would be required for multi‑instance deployments.

9. Summary

The TranscriptAudio.Presentation.JSChunk namespace implements a Blazor‑based transcription UI that accepts whole‑file or chunked audio uploads, forwards them to an external Whisper service, and streams progressive results back to the browser via Server‑Sent Events. The architecture cleanly separates UI, service, and transport layers, supports large files through client‑side chunking, and leverages server‑side Razor rendering for consistent HTML updates.
